## 2. note.com 記事構成

### タイトル案
**「日報を書く15分が、毎日しんどい」を解決するために、SaaSを作った話**

### 記事構成（約3,000〜4,000字想定）

#### 導入（400字）
- 日報にまつわる「あるある」描写から入る
- 18時の憂鬱、Slackで「日報まだの人〜」とリマインドされる気まずさ
- 読者の共感を掴むパート

#### 1. 日報の何が問題なのか（600字）
- 毎日15分 x 年間約250日 = 年間62.5時間（チーム10人なら625時間）
- 「特になし」「順調です」問題 -- 形式的で価値がない
- 提出率50〜70%が現実 -- 忙しい人ほど書かない
- マネージャー側も読むのが苦痛
- **数字を入れて具体的に問題の大きさを見せる**

#### 2. でも日報をやめるのは違う（500字）
- 日報の目的（進捗可視化、課題早期発見、ナレッジ蓄積）は正しい
- 日報をやめたチームで起きた問題のエピソード（仮想的でOK）
- 問題は「日報そのもの」ではなく「手動で毎日書く」という手段
- **ここで読者の「確かに」を引き出す**

#### 3. Slackにはもう全部書いてある（500字）
- 1日のSlackメッセージ量は1人あたり30〜100件
- やったこと、相談、決定事項 -- 全部Slackにある
- 「2度書き」させるのは非効率
- 「Slackの会話をAIが日報にすればよくない？」という発想

#### 4. NipoAIを作った（800字）
- 個人開発者として作った経緯（Build in Publicスタイル）
- Slack連携1分、チャンネル選ぶだけ
- AIが構造化された日報を生成（Slack AIの要約との違い）
- スクリーンショット2〜3枚（ダッシュボード、生成された日報の例）
- **製品の具体的な使い方を見せるパート**

#### 5. 「書く日報」から「確認する日報」へ（400字）
- 日報の価値が変わる -- 書く行為から、内容を振り返る行為へ
- 提出率100%が現実になる
- マネージャーが読んで実際に有用な日報

#### CTA・締め（300字）
- Freeプランでクレジットカード不要
- nipoai.app へのリンク
- 「日報に15分かけてるチームは、ぜひ一度試してみてください」
- Build in Publicで開発を続けるので、Xもフォローしてほしい旨

### note記事の執筆ポイント
- 一人称は「僕」、カジュアルだけど誠実なトーン
- 企業のプレスリリース調は絶対避ける
- 自分の実体験ベースで書く
- 日報の「しんどさ」への共感が最重要

## 3. Zenn / Qiita 技術記事構成

### タイトル案
**「Slack APIとGPT-4o-miniで日報を自動生成するSaaSを個人開発した話」**

### タグ
`Next.js` `Slack API` `OpenAI` `個人開発` `SaaS`

### 記事構成（約4,000〜5,000字想定）

#### 導入（300字）
- NipoAIの概要を1段落で
- この記事で書くこと: Slack APIでのメッセージ取得 → AIでの日報生成 → 技術的に工夫した点

#### 1. アーキテクチャ概要（500字）
- 全体構成図（テキストベースでOK）
```
Slack OAuth → チャンネル選択 → Cron起動
  → Slack API (conversations.history)
  → メッセージ前処理 (preprocessMessages)
  → OpenAI GPT-4o-mini (構造化プロンプト)
  → parseReportContent
  → Supabase upsert
  → ダッシュボード表示
```
- 技術選定の理由（Next.js App Router, Supabase, Vercel）

#### 2. Slack API連携の実装（1,000字）
- OAuth 2.0フロー（Bot Token Scope設計）
- 必要なスコープ: `channels:join`, `channels:history`, `channels:read`, `chat:write`, `users:read`
- `conversations.history` でのメッセージ取得
- タイムゾーンのハマりポイント（JSTでの日付境界計算）
  - **実際にバグった話**: `getStartAndEndOfDayUnix` でJST 15時以降のメッセージが範囲外になった
  - 修正方法とテスト
- Bot Tokenの暗号化保存（AES-256-GCM）

#### 3. AIによる日報生成（1,200字）
- メッセージの前処理（`preprocessMessages`）
  - ノイズ除去（bot投稿、リアクションのみ等）
  - ユーザー名の解決
  - 時系列ソート
- プロンプト設計の考え方
  - 「要約」ではなく「構造化された日報」を生成する
  - 出力フォーマット: やったこと / 課題・相談事項 / 明日の予定
  - Slack AIとの差別化ポイント
- GPT-4o-miniを選んだ理由（コスト: 約¥3.6/ユーザー/月）
- `parseReportContent` でのレスポンスパース

#### 4. 本番運用で工夫した点（800字）
- Cron設計（Vercel Cron Jobs）
- RLS（Row Level Security）でのマルチテナント分離
- Stripe課金との連携（プランに応じた生成回数制限）
- シークレット管理: Infisicalの採用理由

#### 5. 開発期間とコスト（500字）
- 個人開発で約2週間（実質的なコーディング時間）
- 月間ランニングコスト: Vercel Pro + Supabase Free + OpenAI API
- Claude Codeを開発に活用した話（任意）

#### まとめ・CTA（300字）
- 学んだこと（Slack API、AI活用、個人開発SaaSのリアル）
- NipoAI自体の紹介とリンク（nipoai.app）
- Build in Publicで開発中、Xアカウントへの誘導
- 「いいね・ストックしてもらえると励みになります」

### 技術記事の執筆ポイント
- コードスニペットは最低3〜4箇所入れる（特にSlack API周りとプロンプト設計）
- 実際にハマったバグ（タイムゾーン問題）を正直に書く -- 技術記事の読者はリアルな失敗談を好む
- 「宣伝記事」にならないように、技術的な学びを中心に据える
- Zennなら「スクラップ」で開発ログを並行して書くのも効果的
